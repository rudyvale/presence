Ethereum Reverses Course to Fix Validator Deposit Flaw Amid Upgrade Delays

Presence Editorial · October 27, 2026 · 4 min read

After initially planning to discard the proposal, Ethereum engineers integrated a solution for a vulnerability in the forthcoming Glamsterdam upgrade. This issue would have permitted a block constructor to capture ETH meant for a fresh validator by crediting staking funds to builders utilizing an identical public key.

Justin Traglia, acting as maintainer within Ethereum's consensus framework, incorporated the patch on October 26 following avsetsin's discovery of processing errors during the Gloas fork. The adjustment distinguishes between builder and validator deposits based on withdrawal credentials, ensuring that capital does not mistakenly enter an incorrect account when both entities share a public key.

Flaw Could Have Misdirected Staking Funds to Builders

While the vulnerability pertained to rules in development rather than a confirmed theft from Ethereum's mainnet, developers have integrated the correction into specifications pending implementation and testing by individual consensus clients. This matter arose from modifications intended for Glamsterdam's established proposer-builder separation, a framework that divides block construction and proposal duties: builders compile transaction payloads while validators handle proposing and confirming blocks within Ethereum's proof-of-stake architecture.

On October 12, researcher avsetsin outlined the flaw regarding rules governing deposits pending network upgrades. The specific risk involved scenarios where a builder registered under a public key prior to a validator deposit arriving with that same key, potentially causing the proposed logic to credit both deposits to the builder.

On October 12, researcher avsetsin detailed a vulnerability within the deposit rules governing pending network upgrades, specifically under Glamsterdam's proposer-builder separation framework. In this scenario, a staking operator could register as a builder using a public key before a validator deposit arrived with that same key, causing the proposed logic to credit both deposits to the builder balance. Avsetsin warned in a GitHub report that if an operator received funds from a liquid staking protocol to establish a new validator under these conditions, they could manipulate the system so the protocol's validator deposit entered the builder balance where the withdrawal address was under their control. Consequently, avsetsin stated, "The operator can withdraw the protocol's funds," highlighting the risk of misappropriating assets held by the liquid staking service.

In the absence of the anticipated validator creation, a staking provider might fail to secure the necessary proof required for standard deposit and recovery workflows. An investigator analyzed risks associated with Lido, Origin, and Rocket Pool via initial code inspection, emphasizing that these conclusions depended on how each protocol managed deposits. The analysis did not confirm an actual breach by these entities but instead described the theoretical operation of the vulnerability under particular handling circumstances.

Although the researcher highlighted a deposit-routing risk, Ethereum client developers pushed back against the suggested fix. Traglia ultimately shut down the pull request on October 19 following talks with core developers, noting that client support was insufficient to implement the change at that moment.

Developers later reversed that stance and reopened the proposal for review on October 23 after additional scrutiny. Reviewer potuz gave approval but asked for further testing of particular deposit scenarios; Avsetsin then implemented those tests on October 23, addressing situations where builder and validator deposits use a shared public key yet need distinct processing.

On October 26, Ethereum's consensus specifications incorporated the concluding adjustment after further scrutiny by clients. This revision channels valid validator deposits into the validator queue and enables legitimate builder deposits to either register anew or contribute funds to an existing builder.

Withdrawal credentials now differentiate deposits, establishing permitted withdrawal arrangements and maintaining distinct records for builders and validators even when a single public key occupies both roles. The specification update coincided with Ethereum developers examining a separate issue impacting Glamsterdam's planned activation on the Hoodi testnet; consequently, researchers flagged compatibility risks related to EIP-8037, prompting the Ethereum Foundation to delay the October 26 upgrade.

Following a choice to delay the upgrade, Ethereum developers stripped Hoodi's activation schedule of both the Amsterdam execution updates and the Gloas consensus modifications. This postponement also pushed back plans to raise the gas limit cap to 200 million.

Toni Wahrstätter, an Ethereum researcher, noted that EIP-8037 poses risks to smart contracts dependent on specific assumptions regarding remaining gas during execution. He pointed out scenarios where accounting for gas might trigger unexpected transaction reverts or enable execution paths previously thought impossible.

Community Debate and Technical Resolution Followed Quickly

On October 22, representatives from the Ethereum Foundation delayed rolling out EIP-8037 to allow additional scrutiny regarding its compatibility with current smart contracts. While this specific issue regarding contract interaction differs from the builder-deposit error resolved via a separate GitHub fix, both relate to the Glamsterdam upgrade trajectory. Prior to this delay, engineers had reviewed modifications to block building and increased transaction throughput following Glamsterdam's activation on the Sepolia testnet on October 6; however, the planned Hoodi rehearsal has no set date for deployment on the main Ethereum network.

The updated deposit fix includes regression tests that verify how deposits are categorized throughout the Gloas transition phase. Software development teams are required to integrate these specification adjustments into their codebases and finish necessary validation steps before the new regulations can function in an upcoming network update.
